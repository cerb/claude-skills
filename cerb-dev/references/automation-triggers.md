# Automation triggers & the `record.bulkUpdate` bulk wiring

Two separate jobs are documented here:

- **Part 1** — registering a *new automation trigger/event* (the generic 4-spot checklist).
- **Part 2** — wiring the `record.bulkUpdate` trigger into a record type's *bulk update popup* (the per-record-type spots that are easy to miss — there are ~20 of them).

Reference commit for both: `5c26244c06` (added the `record.bulkUpdate` trigger and wired it across every bulk-updatable record type).

---

## Part 1 — Register a new automation trigger/event

A trigger needs **four** edits. Missing any one leaves the event invisible, unregistered, or absent from fresh installs.

### 1. Trigger class
`features/<plugin>/api/automations/triggers/<event_name>.php`, class `AutomationTrigger_<Name>` extends `Extension_AutomationTrigger`. Define `const ID` (the extension id) and `const EVENT_NAME` (the dotted event name, e.g. `record.bulkUpdate`).

Implement the method surface (see `features/cerberusweb.core/api/automations/triggers/record.bulk_update.php`):
- `renderConfig(Model_Automation $model)` — usually assigns `getInputsMeta()`/`getOutputsMeta()` and displays `automations/triggers/config_inputs_outputs.tpl`.
- `validateConfig(array &$params, &$error=null)`
- `getInputsMeta() : array` — the placeholders the automation receives (`state`, `record_type`, `worker_*`, `inputs.*`, …). Each entry: `key`, optional `type` (`array`/`number`/`record`/`dict`), optional `params` (e.g. `record_type`), `notes`.
- `getOutputsMeta() : array` — keyed by `return`; documents `__exit` outputs.
- `getUsageMeta(string $automation_name) : array` — finds linked `automation_event_listener` rows.
- `getEditorToolbarItems(array $toolbar) : array`
- `getAutocompleteSuggestions() : array`

### 2. `plugin.xml` extension (point `cerb.automation.trigger`)
```xml
<extension point="cerb.automation.trigger">
    <id>cerb.trigger.record.bulkUpdate</id>
    <name>record.bulkUpdate</name>
    <class>
        <file>api/automations/triggers/record.bulk_update.php</file>
        <name>AutomationTrigger_RecordBulkUpdate</name>
    </class>
    <params>
        <param key="description" value="Fires for each batch of records during a bulk update, as well as once at the start and once at the end." />
        <param key="features">
            <value><data key="inputs" /></value>
        </param>
    </params>
</extension>
```
Run `/update` after editing `plugin.xml` (see `references/plugin-xml.md`).

### 3. Migration patch — INSERT the `automation_event` row
In the current patch file (`features/cerberusweb.core/patches/11.x/11.2.0.php`), guarded so re-runs are safe:
```php
if(!$db->GetOneMaster("SELECT 1 FROM automation_event WHERE name = 'record.bulkUpdate'")) {
    $db->ExecuteMaster(sprintf('INSERT IGNORE INTO automation_event (name, extension_id, description, automations_kata, updated_at) VALUES (%s,%s,%s,%s,%d)',
        $db->qstr('record.bulkUpdate'),
        $db->qstr('cerb.trigger.record.bulkUpdate'),
        $db->qstr('Fires for each batch of records during a bulk update. Also fires once at the start and once at the end.'),
        $db->qstr(''),
        time()
    ));
}
```

### 4. `install/sql/cerb_base_rows.sql` — seed row for fresh installs
Add the matching `automation_event` row (next sequential id) so new installs get the event without running the patch:
```sql
INSERT INTO `automation_event` VALUES (17,'record.bulkUpdate','Fires for each batch of records during a bulk update, as well as once at the start and once at the end',UNIX_TIMESTAMP());
```
(The patch and the baseline row must agree. This file is regenerated by `tools/dump-baseline-rows.sh` — see `references/baseline-sql.md`.)

## Part 2 — Wire `record.bulkUpdate` into a record type's bulk popup

The central helper is **`\Cerb\Records\BulkUpdate`** (`features/cerberusweb.core/api/Records/BulkUpdate.php`). Each record type's profile/page-section that renders a bulk popup needs **three** edits, and its `bulk.tpl` needs **one**. The AJAX endpoint that renders each automation's input prompts already exists centrally (`PageSection_ProfilesAutomation::_profileAction_getBulkUpdateInputs`, action `getBulkUpdateInputs`) — you do **not** add it per record type.

### A. In the bulk-panel render action — assign `bulk_automations`
Just before `$tpl->display(...the bulk.tpl)`:
```php
$tpl->assign('bulk_automations', \Cerb\Records\BulkUpdate::getMenuItems(
    Context_Ticket::ID,   // or CerberusContexts::CONTEXT_*, or $context for abstract custom records
    $view_id,
    '',
    $active_worker
));
```

### B. In the bulk-POST handler — guard with `handleBulkPost`
Right after the existing `$do = DAO_CustomFieldValue::handleBulkPost($do);` line, **before** enqueuing the job. `start`-state automations can abort the whole job, so bail with a JSON error on `false`:
```php
// Do: Automations
$context = CerberusContexts::CONTEXT_TICKET;
$error = null;
if(false === ($do = \Cerb\Records\BulkUpdate::handleBulkPost($do, $context, $view, $active_worker, $error))) {
    DevblocksPlatform::services()->http()->setHeader('Content-Type', 'application/json; charset=utf-8');
    echo json_encode([
        'status' => false,
        'error' => $error ?: 'Aborted by automation',
    ]);
    return;
}
```

### C. Enqueue via the helper (not the old records service)
The bulk-update job API moved off `DevblocksPlatform::services()->records()` onto `\Cerb\Records\BulkUpdate`. Replace:
```php
// OLD:
$queue_job = DevblocksPlatform::services()->records()->createBulkUpdateJob($view, $do, $active_worker->id ?? 0);
// NEW:
$queue_job = \Cerb\Records\BulkUpdate::createJob($view, $do, $active_worker->id ?? 0);
```
The queue-consumer hooks moved too (`QueueConsumer_Internal`): `processQueue()` and `onJobComplete()` are now static on `\Cerb\Records\BulkUpdate`.

### D. In the `bulk.tpl` template — include the picker
After the `peek_custom_fieldsets.tpl` include, render the "Run Automation" menu when handlers exist:
```smarty
{if $bulk_automations}
{include file="devblocks:cerberusweb.core::internal/views/bulk_automations.tpl"}
{/if}
```
(`bulk_automations.tpl` reads the `$bulk_automations` array assigned in step A; no extra variables needed.)

### Record types already wired (follow these as templates)
Any **new** record type with a bulk popup must repeat A–D. Existing wired profiles:

- **core:** `profiles/{ticket,contact,organization,address,comment,draft,group,task,worker,snippet,queue_job,attachment,abstract_custom_record}.php`, `uri/internal/notifications.php`
- **plugins:** `cerberusweb.timetracking/.../time_tracking.php`, `cerberusweb.calls/.../call.php`, `cerberusweb.crm/.../opp.php`, `cerberusweb.datacenter.domains/.../domain.php`, `cerberusweb.datacenter.servers/.../server.php`, `cerberusweb.feed_reader/.../feed_item.php`, `cerberusweb.kb/.../kb_article.php`

Their matching `bulk.tpl` files each got edit D (e.g. `templates/tickets/rpc/bulk.tpl`, `templates/internal/abstract_custom_record/bulk.tpl`, `templates/contacts/orgs/bulk.tpl`, …).

### Gotcha
`getMenuItems()` takes the **context string** for the record type. For abstract custom records pass the resolved `$context` variable; for fixed types pass the `Context_*::ID`/`CerberusContexts::CONTEXT_*` constant. Passing the wrong context silently yields an empty menu (no error).
